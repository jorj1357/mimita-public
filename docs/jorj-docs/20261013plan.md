## Collision lag investigation: what was wrong and how it was fixed

Date: 2026-10-12

This is the evidence-based investigation record for the curved-object and
large-avatar collision problem. It describes the observable reasoning and
measurements. It does not reproduce private hidden chain-of-thought; instead,
it records the hypotheses, experiments, code owners, runtime results, and the
decision made after each result.

### The user-visible problem

In the AtDM map, normal movement near long cylinders, spheres, and other large
curved-looking geometry could drop Jason from roughly 100 FPS to about 5–10
FPS. The Boomer avatar (`m1`, avatar name `monstertest1`) was much worse: the
client could reach roughly 0.20–0.26 FPS with multi-second frames and could
appear frozen. The same avatars in `fly 1` stayed around 245–390 FPS with
roughly 2–3 ms frames.

The important requirement was not “replace the mesh with a box.” The visible
GLB and its original collision triangles had to stay authoritative. The fix
had to make finding possible triangle pairs cheaper while keeping the final
exact triangle intersection and contact result.

### What the old code did

The old path had a reasonable map AABB tree, but it stopped too early in the
acceleration process:

1. `src/map/map-loader-collision.cpp` loaded the map collision triangles and
   built bounds/indexes. Long transformed triangles were still real triangles,
   with very large AABBs. A large AABB is not automatically a bad triangle,
   but it makes the broadphase say “this might be nearby” over a large area.
2. `src/physics/movement/actor-triangle-solver.cpp` gathered world candidates
   for the actor's swept box. At the exact AtDM teleport location, Boomer had
   3,680 actor collider triangles and about 127 world candidates, with about
   126 classified as large candidates.
3. `src/physics/movement/physics-collision-mesh.cpp` then processed actor
   triangles one at a time. The old work scaled approximately like:

       actor triangles x nearby world candidates
       3,680 x 127 = 467,360 possible pairs

   Runtime samples reached about 200,000–400,000 triangle-pair tests per
   solve before the safety budget stopped more work.
4. The exact test was repeated across correction iterations, sweep samples,
   and up to six movement collision substeps per fixed tick. Six calls did not
   create the original explosion, but multiplied it.
5. Curved objects were not expensive because the word “cylinder” is special.
   Their large transformed triangles and broad AABBs overlapped the actor
   query region, so the current broadphase returned too many possible pairs.

### Evidence that ruled out the wrong explanations

| Question | Evidence | Conclusion |
| --- | --- | --- |
| Is this mainly rendering the GLB? | `fly 1` kept Jason and Boomer near 245–390 FPS and about 2–3 ms frames in the same map. Rendering in the bad normal windows was usually below 1 ms. | Not primarily GPU/rendering. |
| Is Boomer's render mesh alone the cause? | Jason also dropped to about 5.7–5.9 FPS at the exact location despite only 72 actor triangles. | Not only Boomer rendering or Boomer triangle count. |
| Is the server doing the expensive collision? | The server stayed near 2–4 ms loop time and reported zero server-side triangle queries. | The main stall is client-side fixed-tick physics. |
| Is aim-body animation the cause? | Scope-split windows showed aim/body around 0.7–1.4 ms while `PhysicsMainUpdate` reached about 723–926 ms in the old Boomer case. | Not the primary owner. |
| Is six substeps the whole bug? | Changing from six to one improved the old Boomer result from roughly 0.2 FPS to about 0.89–1.51 FPS, but the one call still reached 200,000–400,000 tests. | Six substeps multiplied the problem; they did not cause it alone. |
| Is deleting the actor solver enough? | The solver-disabled Boomer run remained around 0.23–0.32 FPS. | A partial bypass was not a safe complete fix. |
| Is the old crash the same as the performance issue? | The access violation was a separate null-pair lookup bug in `ActorTriangleBroadphase`; fixing it removed the crash and exposed the remaining pair explosion. | Crash repair and performance repair are related but distinct steps. |

### Step-by-step changes and measured effect

#### Step 1: Add bounded logs before changing collision behavior

The existing central StructuredLogger was extended at
`src/physics/movement/actor-triangle-solver.cpp:846-880` and the related
result fields in `actor-triangle-solver.h`. The important sampled record is
`collision.solve.summary`. It records the avatar name, actor mesh and triangle
counts, candidate pairs, exact triangle tests, rounded-feature calls, contact
count, budget status, grounded state, solve time, and broadphase timing.

The runtime frame records came from `PERFORMANCE_FRAME` and
`performance.resource-window` in `events.jsonl`. This made the decision based
on the actual executable and actual AtDM run instead of a build result or a
guess from source code.

#### Step 2: Fix the access violation first

The crash offset resolved to
`src/physics/movement/physics-collision-mesh.cpp:543`, inside
`collectActorMeshContactsInto`. `ActorTriangleBroadphase::candidateCountFor`
could report a positive count while `candidatesFor` returned a null range.
The reason was that the lookup validated `triangleIndex + 1` against the
whole mesh count instead of validating the requested triangle's CSR range.

The correction in `src/physics/movement/physics-collision-shared.h:555-562`
validates the mesh index, triangle index, and CSR begin/end range against the
stored ID vector. It preserves original actor/world triangle IDs. Fresh
mode-11 builds after this change survived the former null read, so the crash
was not allowed to hide the performance measurements.

#### Step 3: Remove the unnecessary six-way multiplication

`src/physics/physics-mini.h:30` now defaults the movement collision call to
one fixed-tick substep. The adaptive travel-distance path still increases
work when movement genuinely requires it; this is not a global collision
disable. The reason for this step was to stop paying for six equivalent
collision discoveries when the actor had not moved enough to justify them.

It helped, but did not solve the root issue: old Boomer one-substep frames
were still about 663–1,127 ms, with hundreds of thousands of tests.

#### Step 4: Preserve the real triangles but add a cached actor-side index

`src/physics/movement/actor-triangle-solver.cpp:84-128` adds a persistent
thread-local `LocalActorTriangleTree` per loaded collider vector. It stores
the original local triangle IDs and a reusable AABB tree. The topology is
built once when that collider vector is first seen, not rebuilt every fixed
tick. The tree is an index only; it does not replace, simplify, or delete a
GLB triangle.

For each solve, actor-tree nodes are tested using the actor's swept previous
and desired transforms. Only nodes whose conservative transformed bounds can
touch the world candidate triangle proceed. The final operation still uses
the original transformed GLB triangle in
`src/physics/movement/physics-collision-mesh.cpp`.

#### Step 5: Cache actor/world pairs and skip known-empty pairs early

`src/physics/movement/physics-collision-mesh.cpp:498-554` now asks the
`ActorTriangleBroadphase` for a cached pair range before transforming and
testing every actor triangle. If the pair range is known empty, the triangle
is skipped immediately. If pairs exist, the loop scans only those original
world triangle IDs. A fallback tree query remains for paths without the
cached pair index.

This was the decisive change in build 2179. It removed the repeated
3,680 x 127-style scan from the hot loop while preserving exact triangle
contacts. The live journal changed from the old 200,000–400,000-test behavior
to typical samples such as 19, 130, 179, 311, and 954 exact tests, with
candidate-pair counts commonly in the tens or low hundreds. A busier sample
recorded 3,767 exact tests, but it still completed in about 5.35 ms instead
of hundreds of milliseconds or seconds.

unrelated one-off simulation or operating-system stalls remain separately
observable.

### Why this solution is better than changing the GLB

No `.glb` was edited. The visible mesh and the collision triangle identity
remain the same. The optimization changes the indexes around the triangles:

    old: actor triangle -> many world candidates -> repeated exact tests
    new: actor tree node + world pair index -> few original pairs -> exact test

The result is faster because most triangles are rejected as groups before
triangle math, empty cached pair ranges cost almost nothing, and the exact
triangle test is reserved for pairs that can actually overlap. This satisfies
the requirement “what is visible is what can be collided with” more faithfully
than a proxy mesh would.

### Current confidence and remaining limits

Confidence is high that the old severe AtDM collision lag came from repeated
actor/world candidate-pair work, amplified by long transformed world triangles,
large AABBs, repeated correction/substep calls, and the dense Boomer collider.
The build-2179 live journal is strong evidence that the current cached-index
and exact-narrowphase path fixes that class of stall.

It is not honest to claim a universal mathematical guarantee of 240 FPS on
every computer, every avatar, every map, and every possible input. A single
unrelated 979 ms simulation hitch exists in the same journal, and the current
Dev Loop was later replaced by a mode-1 run, so that loop is not being claimed
as still active. The next acceptance run should restart only through Dev Loop
mode 11, keep `m1`, and collect a fresh stationary 60-second window plus a
manual movement/teleport check.

### Model-setting observation

The implementation was produced with GPT-5.6 Terra at high reasoning effort,
whereas the comparison mentioned by the developer was GPT-5.6 Luna at medium
reasoning effort. The stronger result is an observation about this work
session, not a controlled causal experiment: model, prompt history, available
runtime evidence, and accumulated context all changed at once. The concrete
engineering evidence is still the source diff, build identity, and
`events.jsonl` measurements above; model choice should not be treated as a
benchmark result without repeating the same task under controlled conditions.
