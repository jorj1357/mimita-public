## Dev-loop launch UX: exact current behavior and target behavior

### Purpose

This section defines the launch experience required when an AI starts the game
through `devscripts/dev-loop.py`. The AI must continue to launch the real
MiMITA executable so runtime behavior and `events.jsonl` remain authoritative.
The change is about process presentation, Windows focus, cursor ownership, and
firewall consent—not about replacing the real game with a fake test process.

### Current observed behavior

The current AI launch path is partially correct:

1. The AI starts the game through the repository dev loop.
2. The dev loop builds or selects a published `.exe` and starts the dedicated
   server and client.
3. The client receives `--unlock-cursor`, so the gameplay cursor policy is
   intended to start unlocked. Pressing `L` remains the in-game lock/unlock
   toggle and must continue to work.
4. The launch creates two visible console windows, generally one for the
   dedicated server and one for the client or launcher process.
5. A newly published executable can cause Windows Firewall to display a modal
   question such as “Do you want to allow public and private networks to
   access this app?”
6. The console windows and the firewall dialog can become the foreground window
   while the user is typing in ChatGPT or another text box. This steals
   keyboard focus and makes the AI launch interrupt writing.
7. Because builds use different executable paths or identities, the firewall
   prompt can recur for later `.exe` launches instead of behaving like a
   one-time consent step.

The observable user-visible failure is therefore:

> While the user is writing, an AI test launch can create two console windows
> and a Windows Firewall modal dialog. One of those windows becomes foreground,
> the text box loses focus, and the user must dismiss or rearrange unrelated
> windows before continuing to write.

### Ideal behavior

For every AI-initiated dev-loop launch:

1. The AI still launches through `devscripts/dev-loop.py`.
2. The real newly built or published `.exe` still runs.
3. The client launch always includes `--unlock-cursor`.
4. The client starts with the gameplay cursor unlocked. The cursor must not be
   captured merely because the AI launched the game.
5. Pressing `L` once in gameplay locks the cursor; pressing `L` again unlocks
   it. The launch policy must not disable or bypass this existing behavior.
6. The dedicated server runs without a visible console window.
7. The client runs without a visible console window unless the selected test
   explicitly requires a visible game window for visual or human acceptance.
8. The dev-loop controller does not open an additional full-screen or
   foreground command window for each test. If a controller window must exist,
   it remains minimized/hidden and is not the foreground window.
9. No launch-owned console or game-support window becomes the topmost/active
   window over the user's current text editor, browser, or ChatGPT textbox.
10. No Windows Firewall consent dialog appears during ordinary repeated AI
    launches. In particular, building a new numbered `.exe` must not result in
    another modal public/private network question.
11. Network access remains deliberate and safe. The solution must not silently
    grant public-network access merely to hide the dialog. The intended rule
    should be documented as local/private development access, with public
    access disabled unless a human explicitly requests and approves it.
12. Runtime evidence remains available through the canonical `events.jsonl`
    path and the dev-loop status/control path even though supporting windows
    are hidden.

### Observable acceptance contract

The behavior is complete only when all of these can be observed on a fresh AI
launch:

| Area | Current result | Required result |
| --- | --- | --- |
| Launch owner | AI uses the dev loop | AI still uses the dev loop; no competing manual launcher |
| Executable | Real `.exe` runs | Real published `.exe` runs and is identified in status/version evidence |
| Cursor at startup | Launch can capture the cursor | Cursor starts unlocked; `MouseLock::locked()` is false after client startup |
| `L` behavior | Existing toggle exists | `L` still changes locked → unlocked and unlocked → locked |
| Server console | Visible console appears | Server process is headless/hidden |
| Client console | Visible console may appear | Client support console is hidden; only an explicitly requested visual game window may be visible |
| Window focus | Console/dialog can steal focus | User's current window remains foreground; launch support windows do not activate over it |
| Window size | Console can occupy a large area | No console takes over the screen; hidden is preferred, minimized is the fallback |
| Firewall | New executable can prompt repeatedly | No modal firewall prompt appears on repeated AI launches |
| Firewall scope | Prompt asks public/private access | Development authorization is private/local only unless explicitly approved otherwise |
| Evidence | Logs may be hard to see without consoles | Exact executable identity, process role, launch arguments, and `EVENTS_JSONL_PATH` remain inspectable |

### Required launch modes

The design should distinguish these cases instead of applying one visibility
policy to every use:

#### `ai-headless`

- Hidden dev-loop controller.
- Hidden dedicated server.
- Hidden client when the test is command/state/network based.
- Structured logs and process status are the output.
- No window may take focus.

#### `ai-visual`

- Hidden dev-loop controller.
- Hidden dedicated server console.
- One visible MiMITA game window for visual or human review.
- Cursor starts unlocked.
- The game window must not be accompanied by support consoles or a firewall
  dialog.
- If Windows requires the game window to be activated for rendering, that
  activation must be an explicit visual-test choice, not an accidental side
  effect of every AI launch.

#### `human`

- Preserve the ordinary human launch behavior unless a human selects a
  different mode.
- Do not hide diagnostic output that a human intentionally requested.

### Implementation boundaries to preserve

- `devscripts/dev-loop.py` remains the launch/process owner.
- `MouseLock` remains the single owner of gameplay cursor lock state.
- `L` remains the existing gameplay action; do not add a second cursor state or
  a second toggle implementation.
- `StructuredLogger` and the canonical `events.jsonl` remain the diagnostic
  owner; do not replace hidden consoles with unmanaged debug files.
- Server lifetime and client lifetime remain separate. Hiding a server window
  must not make leaving the client terminate a healthy dedicated server.
- A hidden process is still a live process: status, exit code, PID, build
  identity, and journal path must remain observable through the dev loop.
- Firewall configuration is an operating-system/development-environment
  concern. It must not be solved by weakening the game's network authority or
  by silently enabling public exposure.

### Verification sequence after implementation

Use a fresh AI launch through the dev loop and record:

1. The dev-loop status before launch, including the selected build and profile.
2. The exact client and server arguments after launch.
3. The exact executable's `--versioninfo` output and `EVENTS_JSONL_PATH`.
4. The number and visibility of console windows.
5. Which window is foreground immediately before and after launch.
6. Whether the user text box remains focused.
7. The startup cursor state in the runtime journal.
8. One `L` press that locks the cursor and a second `L` press that unlocks it.
9. Whether any Windows Firewall dialog appears.
10. The server and client exit/status results after the bounded test ends.

The runtime report must separate “no prompt observed in this run” from a
stronger environment claim that the development firewall rule has been
installed and remains valid for the next newly published executable.

### What this request does not mean

- It does not mean skipping the real `.exe`.
- It does not mean deleting the dev-loop process or its status/control path.
- It does not mean suppressing `events.jsonl` evidence.
- It does not mean granting public network access without review.
- It does not mean forcing every human or visual test to be invisible.
- It does not mean changing gameplay cursor behavior beyond the explicit
  AI-launch startup policy.
