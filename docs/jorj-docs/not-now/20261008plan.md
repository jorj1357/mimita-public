# NPC AimBody Hybrid Mode and Universal Triangle Actor Collision

## Summary

Extend the existing player `AimBodyConfig` hybrid mode to NPCs without creating a separate NPC body-animation system.

NPCs will use:

- the same hot-reloadable `config/aimbody.json`;
- the same physical-body-plus-animation-spring behavior;
- the same right-arm/weapon aiming motor, driven by NPC weapon and target aim instead of camera/RMB input;
- the same triangle collision representation as players.

Ragdolls remain physics-owned and will contribute their current physical limb triangles to the shared actor solver. They will not be converted into AimBody hybrid mode.

Players, NPCs, and ragdolls will eventually enter one fixed-60-Hz actor collision pipeline.

## Specification/document updates

Add a normative section to `docs/architecture/collision/actor-vs-actor-collisions.md` defining:

- “NPC hybrid mode” means the exact existing AimBody hybrid behavior: physical body simulation plus springs toward the procedural animation pose.
- NPCs use the same `aimbody.json` values as players.
- NPCs do not use a literal camera or keyboard/RMB state. Their equivalent aim input is:
  - current weapon target direction when a target exists;
  - current weapon/facing direction when no target exists.
- The same right-arm pointing motor and weapon attachment rules apply.
- The final NPC pose order is:

  ```text
  NPC animation/procedural pose
  → NPC weapon/target aim
  → AimBody hybrid physical solve
  → final body-part transforms
  → triangle collision meshes
  → rendering and replication
  ```

- NPCs are server-owned. The server generates their hybrid pose and authoritative collision state.
- Player clients may predict and submit their own hybrid pose claims; the server validates them.
- Ragdolls remain physics-owned and feed physical limb triangles into the shared solver.
- Full triangle detection uses manifold aggregation for stable body-level response; each triangle pair does not receive an independent impulse.
- `config/aimbody.json` owns body-animation hybrid tuning.
- Existing collision configuration owns global collision response and limits.
- Actor presets own per-actor mass, friction, restitution, and collision participation overrides.

## Implementation phases

### 1. Shared hybrid body-pose owner

Generalize the existing `RagdollModeSystem`/AimBody path so it can operate on player and NPC actor bodies.

Reuse:

- `AimBodyConfig`;
- existing hybrid spring behavior;
- existing six-limb ordering;
- existing physical tuning in `ragdoll.json`;
- existing weapon/right-arm transform logic.

Add an actor-independent pose input containing:

- root transform;
- procedural limb targets;
- aim direction;
- weapon transform;
- lifecycle identity;
- actor kind.

Player input supplies camera-derived aim. NPC input supplies target/facing/weapon aim.

The final hybrid pose must update both visible transforms and the collision-mesh transforms used by the actor solver.

### 2. NPC lifecycle integration

At NPC spawn, respawn, avatar change, and weapon change:

- initialize the NPC hybrid body state;
- load the same body-part collision triangles used by players;
- preserve lifecycle/transform epoch identity;
- clear old support, pose, and collision state;
- ensure the first valid hybrid pose exists before the NPC participates in actor collision.

NPC navigation remains responsible only for movement intent. It must not directly resolve physical actor collision.

### 3. Shared actor geometry and pair broadphase

Create one actor collision input/provider for:

- players;
- NPCs;
- alive/downed actors;
- ragdolls.

Each actor provides:

- world-space body-part triangles;
- held weapon/tool triangles;
- previous and desired transforms;
- root velocity;
- contact-point velocity;
- mass/friction/restitution;
- lifecycle ID;
- collision participation flags.

Add a fixed-tick actor broadphase using stable actor IDs and cached/reusable scratch storage. Only nearby actor pairs proceed to triangle narrow phase.

The pair solver must use:

```text
actor pair
→ swept triangle candidate pairs
→ triangle contacts
→ merged contact manifold
→ bounded depenetration
→ mass-based response
→ support selection
→ final actor state
```

Pair processing order must be deterministic.

### 4. Shared triangle response

Implement one response owner for player/player, player/NPC, NPC/NPC, and actor/ragdoll contacts.

The response must support:

- equal-mass head-on bounce;
- no-bounce momentum transfer;
- stationary actor pushability;
- heavy-versus-light actors;
- tangential sliding/friction;
- bounded restitution;
- bounded solver-generated separation speed;
- contact-point relative velocity;
- stable manifold aggregation;
- small controlled penetration under dense swarm pressure;
- no numerical energy creation.

Player input remains movement intent. Collision response modifies physical velocity and position; it does not cancel input or make AI decisions.

### 5. Support and moving-actor inheritance

Extend the existing physical-entity support model to actor supports.

Each support contact records:

- `supportActorId`;
- support lifecycle ID;
- supporting body part;
- contact point;
- support velocity;
- inherited velocity.

Rules:

- standing on another actor creates support;
- support motion is inherited;
- the supported actor’s own movement is additive;
- support jumping transfers relevant support velocity;
- sideways support motion carries supported actors;
- support death or ragdoll conversion invalidates the old support;
- the supported actor falls naturally unless another valid support remains;
- ragdoll limbs may provide temporary support.

Support state must be cleared on respawn, teleport, ghost transition, and lifecycle change.

### 6. Network integration

Reuse the existing six-limb `RagdollReplicationPose` transport rather than creating a second unrelated pose format.

Extend the existing transport boundary to include:

- actor kind;
- actor ID;
- lifecycle/transform epoch;
- source simulation tick;
- hybrid/physical/ragdoll mode;
- root transform;
- six-limb world transforms;
- enough pose data for collision reconstruction.

Compatibility rules:

- player clients may send hybrid pose claims;
- the server validates player claims against allowed pose/movement limits;
- the server generates NPC hybrid poses and replicates them;
- ragdoll poses remain server-authoritative physical poses;
- authoritative root position, velocity, support, and collision result remain server-owned;
- clients reconcile predicted actor state to server state;
- stale lifecycle poses are rejected.

Do not claim full server-authoritative triangle collision until the server can construct or validate the same body triangles represented by the pose.

### 7. Bounded evidence logging

Use the existing `StructuredLogger` and canonical `events.jsonl`. Do not create a collision-specific text logger.

Add bounded, filterable events:

- `actor-hybrid.pose-input`
- `actor-hybrid.pose-final`
- `actor-collision.candidate`
- `actor-collision.contact`
- `actor-collision.response`
- `actor-collision.support-changed`
- `actor-collision.reconcile`
- `actor-collision.spawn-overlap`
- `actor-collision.fallback`
- `actor-collision.swarm-summary`

Every sampled event must include:

- simulation tick;
- actor ID and lifecycle ID;
- actor kind;
- collision backend;
- pose source;
- expected versus actual values where applicable;
- reason for acceptance/rejection;
- relevant position/velocity/normal/penetration data.

Default logging is state-change and scenario-filtered, not every pair or triangle every tick.

The first proof run must explicitly show that no actor silently falls back from triangle collision to legacy collision.

## Validation plan

### Deterministic/component validation

Add focused tests for:

- hybrid pose target generation from NPC aim;
- player and NPC pose transform parity;
- triangle provider output;
- stable pair ordering;
- equal-mass response;
- heavy/light response;
- no-bounce momentum transfer;
- frictional sliding;
- manifold aggregation;
- bounded energy;
- support acquisition/loss;
- support velocity inheritance;
- lifecycle invalidation;
- spawn overlap push-out.

These tests prove isolated math and serialization only.

### Real runtime scenarios

Use the real executable and canonical `EVENTS_JSONL_PATH`.

Required scenarios:

1. Player versus player head-on.
2. Player versus NPC.
3. NPC versus NPC.
4. Stationary actor being pushed.
5. Light NPC versus heavy Juggernaut.
6. Actor standing on another actor.
7. Moving support actor.
8. Support actor jumping.
9. Support actor dying and becoming ragdoll.
10. Player/NPC/ragdoll pile.
11. Weapon-first contact.
12. High-speed dash contact.
13. 20-, 64-, and 100-actor doorway/swarm scenarios.
14. Non-host scenario with simulated 100 ms latency.

Required evidence:

- all participants use the same solver owner;
- all contacts identify triangle/body-part pairs;
- response values match configured mass/friction/restitution;
- support transitions are recorded;
- NPC hybrid poses are server-generated;
- player claims are accepted/rejected with reasons;
- prediction error and reconciliation are bounded;
- no legacy fallback occurs silently;
- no actor tunnels through another actor.

### Acceptance metrics

Record and review:

- maximum penetration;
- average penetration;
- solver-created peak velocity;
- energy growth;
- contact sign-change/jitter frequency;
- support stability;
- reconciliation position/velocity error;
- broadphase, narrowphase, and solver time;
- pair count, triangle candidate count, and contact count.

Human acceptance must separately confirm:

- actors feel physical;
- equal walkers bounce but can continue moving;
- heavy actors resist light actors;
- actors slide shoulder-to-shoulder;
- standing and moving support feel correct;
- swarms remain chaotic without becoming rigid walls or exploding.

## Assumptions locked from this planning discussion

- NPC hybrid mode reuses the existing player AimBody hybrid behavior.
- `config/aimbody.json` remains the shared body-animation source of truth.
- NPC aim comes from weapon/target/facing state.
- Players may submit pose claims; the server validates them.
- NPC poses are generated authoritatively by the server.
- Existing pose transport is extended rather than replaced with a second packet system.
- The first rollout includes players, NPCs, and ragdolls.
- Ragdolls remain physics-owned rather than becoming AimBody hybrid bodies.
- The implementation must proceed behind explicit backend/config gates until runtime proof passes.
