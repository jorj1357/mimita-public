# Heavy Shotgun / Juggernaut plan

Date: 2026-10-10 (America/New_York)  
Status: IMPLEMENTED SOURCE/CONFIG — runtime acceptance pending

## Short answer

Yes, this is feasible. The safe shape is a new weapon definition named
`heavy_shotgun`, with its own model, sounds, pellet count, damage, knockback,
tracer recipe, muzzle-flash recipe, and recoil profile. It should be added to
the Juggernaut role/loadout explicitly. It should not replace `shotgun`, and
it should not be implemented as a second one-off C++ shotgun system.

This session focuses on making the weapon real and usable in the actual
Juggernaut role.

## Confirmed repository facts

- Active weapon definitions load from `config/weapons.json`; the loader reads
  model, viewmodel, damage, fire delay, magazine, pellet count, spread,
  recoil, knockback, behavior, hitscan, and sound fields.
- The existing `shotgun` is a separate JSON entry with 15 pellets, 5 damage
  per pellet, a 0.01 second fire delay, and the ordinary shotgun assets.
- `assets/objects/weapons/mimita-heavyshotgun-v1.glb` exists.
- These user-provided assets exist and are currently untracked:
  - `assets/sound/weapon/heavyshotgun/heavyshotgunfire.wav`
  - `assets/sound/weapon/heavyshotgun/heavyshotgunequip.wav`
  - `assets/sound/weapon/heavyshotgun/heavyshotgunreload.wav`
- `config/weapon-tracers.json` is a hot-reloaded per-weapon visual config and
  already supports thickness, end thickness, lifetime, alpha, and RGB color.
- `config/weaponsets.json` currently gives the actual Juggernaut mode role the
  `large_machine_gun` loadout. This will be changed so the actual Juggernaut
  owns `heavy_shotgun`; Fighters will not receive it.
- `src/combat/weapon-fire-effects.cpp` applies shooter knockback and accumulates
  a recoil scalar, while `src/combat/weapon-system.cpp` also has recoil decay
  and a legacy direct recoil path. This is an ownership warning: the
  implementation phase must consolidate the camera recoil owner before tuning.
- `src/camera.cpp::Camera::addPunch()` clamps camera punch, and the current
  camera/recoil feature record requires weapon recoil to stay separate from
  camera sway.
- `config/video-settings.json` already has VSync off and a high frame cap.
  The performance spec forbids re-enabling VSync or moving gameplay work into
  the render loop.

## Requested behavior, translated into testable requirements

### Heavy shotgun identity

- ID: `heavy_shotgun`
- Display name: `Heavy Shotgun`
- New model: `assets/objects/weapons/mimita-heavyshotgun-v1.glb`
- New fire/equip/reload sounds from the three heavy-shotgun asset paths above
- New definition and registry identity; do not mutate `shotgun` or silently
  alias the new ID to it
- Semi-automatic, exactly 1.0 second between shots
- 2.5 second reload, 8-round magazine, and 888 reserve ammunition
- Pellet hitscan with 40 pellets
- Strong Juggernaut-grade damage and victim knockback
- Bright, high-contrast muzzle flash and nearly white tracers
- Intended feel: a heavy, readable `POW`, not rapid shotgun spam

### Values that still need a human decision

The notes say “each does like 35 damage minimum” and “pretty much instant
kill.” Those are not equivalent requirements. Forty pellets at 35 damage can
reach 1,400 raw damage before multipliers, falloff, and blocked pellets. The
implementation should not guess whether that means:

1. 35 damage per confirmed pellet with normal hit rules;
2. a bounded total-damage cap per trigger pull; or
3. a Juggernaut-only execution rule that is authoritative and explicit.

The plan assumes option 1 for the first implementation, with a documented
per-shot damage cap only if live testing proves the uncapped result is unsafe.
“Minimum” must also be defined against distance falloff and limb multipliers.

The notes also say “2x bigger dynamic flash.” The implementation should use
the existing muzzle-flash/dynamic-light owner and define exactly which field
is doubled: light radius, intensity, effect scale, or all three. It must not
create a second dynamic-light manager.

## Proposed implementation slices

### Slice 0 — lock the contract

- Decide the damage interpretation above.
- Confirm the actual Juggernaut role remains the only role receiving the
  weapon. This is now decided: `heavy_shotgun` belongs to the Juggernaut.

### Slice 1 — data and asset registration

- Add `heavy_shotgun` as a complete entry in `config/weapons.json`.
- Add it to the actual Juggernaut role weapon set in `config/weaponsets.json`
  and make it the role's starting weapon. Ensure logical-slot-to-native-slot
  mapping remains one-way and authoritative.
- Add a dedicated `heavy_shotgun` entry to `config/weaponcollisions.json`,
  using the established cached JSON box path and a collider sized for the new
  model. Do not reuse the `shotgun` or `large_machine_gun` collision ID.
- Add the model to asset validation/ownership checks if the current validator
  requires an explicit inventory entry.
- Register the three logical sound resources through the existing weapon/audio
  path. Do not add direct gameplay-only WAV playback or a special sound
  manager. The audio contract requires one audio owner and safe resource
  reload behavior.
- Add any required animation pose entry keyed by `heavy_shotgun`, reusing the
  existing weapon viewmodel/animation owner.

### Slice 2 — firing and authority

- Reuse the generic hitscan pellet path, deterministic spread seed, fixed-tick
  damage validation, and authoritative server result path.
- Verify that 40 pellets are bounded by the existing pellet cap and that the
  server and client use the same definition and spread seed.
- Verify damage aggregation, hit markers, health reduction, death, and
  knockback for players and NPCs without creating a heavy-shotgun-only damage
  system.
- Add bounded structured diagnostics at the weapon owner for definition ID,
  shot ID, pellet count, confirmed hits, total damage, knockback, fire tick,
  and first client/server disagreement.

### Slice 3 — presentation

- Add a `heavy_shotgun` tracer override in `config/weapon-tracers.json`:
  nearly white RGB, approximately `0.3` thickness, approximately `0.9` start
  alpha, and a short readable lifetime. Validate the actual field semantics
  because alpha currently has separate start/end values.
- Add a per-weapon muzzle-flash/dynamic-light recipe through the established
  weapon hit-FX/effect owner. Tune the requested 2x scale at that owner and
  keep the effect bounded by the existing dynamic-light pool.
- Route fire/equip/reload through the heavy-shotgun logical sound IDs and
  verify that local prediction and remote replicated fire use the same sound
  policy without double playback.
- Human review must confirm model orientation, grip, muzzle position, scale,
  flash brightness, tracer readability, and the perceived `POW` sound.

### Slice 4 — recoil redesign and definition

The current `recoil` field is overloaded with at least three different ideas:

- shooter movement impulse / self-knockback;
- camera punch, which is currently clamped and not clearly driven by the
  weapon definition; and
- accumulated weapon/viewmodel recoil that decays over time.

The plan is to split the concepts while preserving one owner for each:

- `self_knockback`: authoritative fixed-tick movement impulse;
- `camera_recoil`: presentation-only pitch/yaw impulse per shot;
- `viewmodel_recoil`: weapon/arm kick amount;
- `recoil_recovery`: return rate or recovery time;
- `recoil_accumulation`: how consecutive shots build spray; and
- optional deterministic `recoil_pattern` data if the AK/CS-style pattern is
  desired rather than random camera noise.

The requested scale should be explicit: `1.0` means no visible camera or
viewmodel recoil, `999.0` means a large but bounded response. The mapping must
be monotonic, finite, clamped, and independent of camera-sway settings.
Recoil must be applied on a shot event, not by repeatedly forcing the camera
to a fixed value. Recovery must use the weapon’s own fields and be evaluated
at fixed tick / presentation boundaries as appropriate.

The implementation uses a deterministic per-shot camera kick plus an
accumulated recoil value with weapon-defined recovery, similar in feel to
CS/AK spray, while keeping aim authority and server damage unchanged. Camera
punch must not alter the authoritative shot direction retroactively.

### Slice 5 — real Juggernaut runtime validation

- Run the actual Juggernaut role with the heavy shotgun, capture
  `--versioninfo` and its exact `EVENTS_JSONL_PATH`, then exercise equip, fire,
  reload, repeated fire, hit, knockback, and death.
- Verify the journal proves the definition ID, role/loadout, 1.0 second fire
  delay, 2.5 second reload, 8/888 ammo state, 40-pellet shot, sound, flash,
  tracer, collision definition, and recoil accumulation/recovery.
- Keep fixed 60 Hz gameplay authority and the existing collision broadphase.

## Acceptance gates

### Source/config gate

- `heavy_shotgun` is a distinct registered definition and appears in the
  intended role’s authoritative weapon set.
- All asset paths resolve, are tracked intentionally, and have a loader or
  validation check.
- Invalid JSON preserves the last valid configuration and emits a categorized
  diagnostic.

### Runtime gate

- The live journal proves definition load, role/loadout selection, fire request,
  authoritative shot result, 40-pellet bound, damage, knockback, audio, flash,
  tracer, and recoil/recovery state.
- Client/server or local/remote results agree on weapon ID, shot ID, tick,
  pellet seed, and authoritative damage.
- Repeated shots obey the 1.0 second delay and recoil decay/accumulation rules.

### Performance gate

- The actual Juggernaut role uses the new weapon and fixed 60 Hz gameplay
  remains unchanged.

### Human gate

- Human playtest confirms the weapon feels huge, the sound is distinct and
  strong, the flash is bright but readable, the model is correct, victims are
  knocked back as intended, and recoil visibly responds to values and decays
  after firing stops.
- Multiplayer acceptance is separate from build and journal evidence.

## Required final evidence

The implementation session should report source/config, build, runtime journal,
performance, and human acceptance as separate claims. It should use the
canonical timestamped executable and write exactly one session changelog.
No feature should be called complete from a successful build alone.
