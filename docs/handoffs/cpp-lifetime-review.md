# C++ lifetime review: first source-traced findings

**Status:** partial source review. The `.cpp` map covers 731 files; this note records concrete lifetime paths inspected in the current checkout. It does not certify any source as safe to unload. The 614 `.cpp` files across current game targets and 18 saved-manifest-only Manifold candidates remain semantically unreviewed in the CSV. The 22 C translation units compiled into the EXE are listed separately and also need lifetime tracing.

## Detached-thread sites requiring a resident executor or generation lease

Source inspection found detached worker entry points at:

- `src/analytics/analytics-uploader.cpp:132-149`: detached HTTP upload closure calls `AnalyticsUploader::postJson` / uploader implementation code.
- `src/avatar/avatar-atlas.cpp:474-489`: detached atlas build writes through a raw pointer into `mPendingAtlas`; the owner can reset that `unique_ptr` on a stale generation (`:496-498`). This is both an unload and object-lifetime hazard until cancellation/ownership is established.
- `src/combat/weapon-model-cache.cpp:130-138`: detached model loader receives a shared asset object; worker code and any referenced services still need module-lifetime protection.
- `src/engine/engine-tick-replay.cpp:1005-1014`: detached validation closure calls `std::system` and returns through module code.
- `src/entities/player-loader.cpp:1341-1357`: detached model loader receives `mPendingModel.get()` as a raw pointer; `src/entities/player-loader.cpp:1392-1408,1463,1519` can reset the owning member. Trace cancellation/ownership before unload or reset.
- `src/network/server-browser.cpp:106-193`: detached refresh worker reads/writes file-static browser state and invokes logging/network helpers.
- `src/replay/replay-export.cpp:705-713`: detached shell-launch closure updates `gExplorerLaunchFailed` after calling `ShellExecuteA`.
- `src/replay/replay-export-json.cpp:431-436`: detached closure calls `std::system` to open Explorer.

A detached thread is not automatically unsafe if it executes only resident code and owns no module data, but these closures/helpers are compiled into the candidate module. The loader must account for in-flight execution; detach itself provides no join/quiescence evidence.

## What this establishes and what remains open

- The source already contains long-lived server/session state, worker threads, static resources, raw async result pointers, and callbacks stored in persistent objects. Those cannot be copied into a replaceable DLL and then forgotten.
- Several current owners have joins/drains, but the review has not established that the canonical runtime invokes them at every reload/exit path or that callbacks/jobs are barred from re-entering during activation.
- This is a targeted manual source trace of high-risk examples. It does not complete the per-file review of 614 current game-target `.cpp` files, 18 saved-manifest-only vendor candidates, 22 EXE C translation units, the rest of the mutable static-state candidate set, all class/object lifetime routes, or all external-resource owners.
- Next review batches should trace all detached/thread/job sites and callback registrations first, then mutable-state candidate files by dependency-connected area. Mark each file reviewed only after tracing construction, all readers/writers, shutdown/reset, and cross-module references.

### Graphics/device ownership

`src/renderer/renderer.cpp` creates GLFW and the window/context, makes the context current, loads GL entry points through `gladLoadGLLoader`, and creates the base shader program (around lines 195-270). `Renderer::shutdown()` deletes its shader, destroys the window, and terminates GLFW (around lines 480-510). The process-owned window/context and GL loader dispatch are host/device lifetime, not replaceable game state.

A source scan found OpenGL allocation/use in 31 C++ files, including renderer, world/map rendering, player/avatar loading, GUI, effects, physics visualization, shadow/post effects, and replay export. Examples include static VAO/cache state in `src/render/render-world-sky.cpp`, `src/physics/physical-entity.cpp`, `src/debug/debug-visuals-lines.cpp`, and `src/combat/projectile-render.cpp`. `GLuint` values are handles to objects owned by the still-live GL context; unloading the C++ code does not delete those GL objects. Before a rendering TU can be replaceable, its persistent GL resources need a registry/owner with explicit release while the context is current, then recreation by the new generation. Keep `glad.c` dispatch and context management resident.

### Network ownership

`MultiplayerContext` is the client session owner for socket/transport and replicated-state caches. `UdpTransport::close()` closes its socket (`src/network/udp-transport.h`), and server shutdown closes its UDP socket and calls `netShutdown`; `src/network/net_common.cpp` owns Winsock startup/cleanup. `ListenServerState` separately owns its socket and ICE resources. `src/network/server-ice.cpp` owns pending ICE peers and coordinator poll state. These are session/transport resources that need an orderly close/drain protocol before the owning implementation is unloaded. `juice_destroy` callback-thread completion remains unverified, as noted above.

### What this pass proves, and does not

- Source evidence confirms persistent state is spread across function-static client objects, process globals pointing to them, session structs, file-static worker state, job queues, and graphics/network handles.
- Some owners already have joins, drains, close calls, or shutdown functions. This is not yet proof that all reload/exit routes call them, or that no callback/job can re-enter during the swap.
- The key migration rule is therefore: keep the execution substrate and resource/session owners resident; make game behavior callable through a stable ABI; add a per-generation quiesce step that blocks new work, unregisters callbacks, waits for in-flight calls/jobs, releases generation-owned GL resources with the context current, then unloads. State that must continue is stored in host-owned versioned records, not in the old DLL's STL objects.
- Not yet reviewed: every candidate source's full construct/read/write/reset path; all 31 graphics-owner files; all callbacks and their unregister semantics; all 39 thread/job candidate files; all current EXE C TUs; external Manifold archive provenance; complete listen-server and client shutdown/reconnect sequences. No file is being marked “safe to unload” from this targeted trace.
- Static-only review; no build, test, runtime launch, or human gameplay validation was performed.

## Existing loader barrier evidence (2026-11-12)

A source trace of the two current loader paths distinguishes what is already protected from what is still missing:

| Path | Evidence-backed protection | Remaining gap before whole-game use |
|---|---|---|
| Focused `HotReloadSystem` | `src/hot-reload/game-api.h` exposes `beforeUnload(GameMemory*)`; `src/hot-reload/hot-reload-system.cpp:79-119` loads/validates a candidate, runs `onReload`, swaps the API, calls old `beforeUnload`, then `FreeLibrary`. `unloadGameDLL` does the same teardown at lines 123-134. | No visible in-flight call counter, dispatch lock, quiesce/refusal result, or generation task/callback registry. The two game API functions are called by other code, so all call sites must be known and stopped before unload. `beforeUnload` is `void`, so it cannot refuse an unsafe unload. The watcher runs `std::system("python build_game_dll.py")` synchronously (lines 163-180) and only watches two `.cpp` files plus `game-api.h` (lines 184-192). This is a narrow proof mechanism, not general save-to-live. |
| Existing subsystem `ModuleHost` | `src/hot-reload/module-host.cpp:1104-1140` holds a shared `mModuleMutex` lock across synchronous `onEvent` dispatch. Reload/shutdown uses the same mutex exclusively (`:945-960,2090`), so it waits for those host-dispatched calls to return before teardown. It validates ABI/name/generation/hash/schema and capabilities, exports/imports bounded state, calls old `shutdown`, swaps entry, then `FreeLibrary` (`:2003-2205`). The module catalog can add/remove entries and refresh source sets (`:1890-1970`). | The lock only covers calls routed through `ModuleHost`; it cannot observe a module-created worker, detached thread, OS/library callback, or callback registered elsewhere. `ModuleV1::shutdown` in `src/modules/api/module-abi.h:152-164` returns `void`, so the host cannot require a quiescence acknowledgement. A failed `initialize` path calls `FreeLibrary` without a visible `shutdown` (`module-host.cpp:2058-2066`), so partial initialization cleanup is not guaranteed by the host contract. This existing mechanism does not prove arbitrary game sources safe to load or remove. |

**Practical meaning:** there is a partial synchronous-call barrier in the existing subsystem host, but no complete game-generation barrier. Before whole-game activation, the boundary must stop all entry routes, prevent new work, drain or cancel and join all work, wait for in-flight calls, release generation-owned resources under the correct device/context, and provide an explicit success/busy result. Candidate initialization must also have a guaranteed cleanup path on failure. The old generation remains loaded until every condition is satisfied.

**Scope note:** module-catalog add/remove evidence applies to declared subsystem modules and their source patterns. It does not prove that adding/removing any arbitrary repository `.cpp`, header, asset, or runtime/host file automatically builds and updates live. That needs a canonical owner manifest, dependency-aware background build coordinator, asset-specific reload routes, and runtime activation proof. Source saves outside the active game-DLL manifest are not hot by default.
