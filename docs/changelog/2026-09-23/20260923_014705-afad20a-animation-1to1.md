## What afad20a animation actually was

`git show afad20a:src/entities/player-animation.cpp`:

- Exactly three clip states: `idle`, `walk`, `return_to_idle`.
- Dash and freeze were **pose overlays**, not clips: a fixed pose blended over
  the locomotion base with a timer (`snapIn` / `blendInTime` / fixed 0.15 s hold
  / `blendOutTime`), using `smoothstep`.
- Idle added a procedural sway (arms/legs/torso/head sinusoids, torso breathing).
- Every part was eased toward the target by an exact semi-implicit spring:
  `accel = (target - value) * stiffness - velocity * damping`,
  `velocity += accel * dt`, `value += velocity * dt` (translation 90/16,
  rotation 80/14).
- No jump/fall/land/dash/down-dash/freeze states, and no cross-fade between
  states (instant switch, then the springs smooth it).

## What was on disk before this session

- idle/walk/return_to_idle already sampled the `afad20a` JSON keyframes, but via
  the JSON path only.
- Dash and freeze were full-body **action clips**, not overlays.
- The spring was an exponential ease (`1 - exp(-k*dt)`), not the exact spring.
- No procedural idle sway.

## What changed

New `src/hot-reload/hot-animation-afad20a.h`:

- `Afad20a::State` (persistent per entity): current clip, `animStateTime`,
  `weaponSwayTime`, `dashPoseTimer`, `freezePoseTimer`, `prevFreezeActive`,
  `aimBodyPitch`, and the exact spring value/velocity for every part/axis.
- The `afad20a` dash and freeze poses as compiled data (from
  `config/player-procedural.json` at `afad20a`), plus the idle sway parameters.
- `stepState`: the three-state machine with the `inputTriggered` walk and the
  `tickBasedReturnToIdle` return clip.
- `dashWeight` / `freezeWeight`: the exact overlay timers.
- `applyOverlay`, `applyIdleSway`, `springStep`: the exact pose build pieces.
- `runAfad20aAnimationSelfTest`: deterministic state-machine, overlay-weight,
  spring, and sway checks.

`src/hot-reload/modules/presentation/pose-generation.cpp`:

- When `HotAnim::afad20aSourceCpp()` is true (`config/animations.json`
  `locomotionSource: "cpp"`), the pose is produced by the afad20a evaluator:
  base clip sampled with `afad20aSampleClip` -> tool action arms (shoot/reload/
  slash) or JSON weapon carry stance -> freeze overlay -> dash overlay -> idle
  sway -> aimbody -> exact spring. The state is read/written through the
  `AfadAnimState` dynamic component (schema registered).
- When `locomotionSource` is `"json"`, the previous JSON/action-clip path runs
  unchanged, so the current animation remains selectable.

`src/hot-reload/modules/presentation/animation-selftest.cpp`:

- Calls the afad20a evaluator self-test in the candidate gate.

`src/hot-reload/hot-modules.json`: registered the new header for change
detection.

## Limits

- Weapon arm poses: afad20a selected per-weapon `weapons.<id>.poses.<state>`
  (equipping/reloading/shooting/just_shot/slash/lunge). The hot path still uses
  the migrated hot tool phases plus the JSON `weaponArms` carry stance; the exact
  `afad20a` weapon pose table selection is not yet wired into the afad20a path.
- The afad20a path runs in the RENDER domain (like the previous pose generation)
  and republishes the stored pose before collision, matching the afad20a
  ordering; this was not re-verified against the render/collision transform
  identity this session.
- Down-dash has no separate afad20a pose (afad20a had none); it only changes
  velocity.
- `behaviorSource: "cpp"` still switches tool phase sets / `weaponArms` / aimbody
  to their compiled paths; `locomotionSource` is the animation-implementation
  selector.
