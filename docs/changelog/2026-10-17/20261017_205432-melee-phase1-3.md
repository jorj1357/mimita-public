Server shield/grab (`src/network/server-melee-actions.cpp`):
- `config/melee.json` loaded for shield/grab/force values.
- Shield: 50 durability; linear decay over 300 held ticks; received percent and
  knockback multiplied by `1 - remainingFraction` (measured before the hit);
  shield damage = move percent unless the action overrides `shield_damage`;
  excess does not spill into percent; break applies the scaled knockback plus a
  fixed 5 m/s upward impulse and plays `melee.shield_break`; natural 300-tick
  depletion breaks identically; broken shields recover 0→full over 120 ticks;
  releasing before break recovers over the configured release window.
- Grab: `grab` action hit starts a pull over `grab_pull_ticks`; the target is
  pulled by a bounded, controllable impulse (percent-scaled velocity cap
  20/40/80→120 m/s); a shielded target blocks the grab (`melee.grab_blocked`);
  a successful grab grants 300 ticks of anti-chain immunity; `melee.grab_start`.
- ServerPlayer shield/grab state reset on spawn.

## Phase 7b — prediction-first referee + revision alignment (implemented slice, build green)

Implemented (bounded, no new packets):
- Move-set **revision alignment**: `mpSendAttackRequest` gained a
  `movesetRevision` parameter carried in the two unused `AttackRequestPacket`
  reserved bytes; the Melee client sends the equipped move set's revision; the
  server compares it to its own and rejects a mismatch with a visible
  disagreement (`melee move-set revision mismatch`).
- **Illegal action index** rejected with a disagreement.
- **In-progress revision retention**: the server snapshots the `MeleeAction` at
  action start (actor-id keyed map in `server-melee-actions.cpp`) and the client
  snapshots it too, so a mid-action `config/weapons.json` hot reload does not
  change an action already underway; new actions read the freshly published
  revision at the next fixed tick.
- Referee checks already present and reused: stale spawn generation (attack
  request validation), duplicate contact (one hit per target per action),
  shield-blocked grab, and impulses clamped to the configured envelope.
- No double impulse on correction: target percent/knockback is applied once by
  the server; the client predicts only its own animation and self-impulse.

Deferred (documented, needs a second message/packet): the client does not yet
send a **contact/hit-claim** at the moment of predicted contact, so the server
does not yet accept a plausible historical client contact against its own miss.
The `AttackRequestPacket.claimedTargetId/claimedHit*` fields and the legacy
`MeleeHitRequestPacket` are the intended reuse points for that slice.
