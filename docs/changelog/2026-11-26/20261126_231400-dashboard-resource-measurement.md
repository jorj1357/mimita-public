# Dashboard resource measurement and refresh-path change

## User request

The user asked to reduce dashboard RAM and CPU, restart and measure the dashboard repeatedly, and write a strong system CPU/RAM measurement specification.

## Source change

In `devscripts/dev-loop.py`, dashboard status collection now reuses the daemon snapshot already fetched for the GUI refresh. This removes one redundant status RPC from every refresh. `python -m py_compile devscripts/dev-loop.py` passed. No C++ build was requested or run; this Python tool change does not change game binaries.

## Measurement and outcome

The dashboard was restarted after the source change as PID 1328. Five-minute measurement artifact `.dev/resource-measurements/20261126T230539Z-dashboard-post-refresh.jsonl` contains 300 one-second samples after 60 seconds of warm-up (322.3 seconds total, 12 logical CPUs).

PID 1328 used 109.36 CPU seconds: 33.93% of one logical CPU and 2.83% whole-host capacity. Mean/p95/max working set was 92.4/122.3/123.1 MB; private memory was 95.6/125.6/126.3 MB. Collector used 0.22 CPU seconds. The target of under 1% whole-host mean CPU and private-memory p95 <=100 MB is not met; working-set p95 <=125 MB is met.

This sample is not a matched A/B. The run changed from `20261126_230039` to `20261126_231000` during measurement, the client was offline by warm-up end, host CPU averaged 84.68% and reached 100%, available RAM fell to 455.6 MB, and commit reached 31,418.8/36,233 MB. The prior 68-second sample was 23.63% of one core / 1.97% whole host; therefore no CPU improvement is demonstrated. Do not infer that dashboard CPU caused host pressure or the user's in-game FPS loss from these samples.

Runtime journals for the first run: `logs/2026-11-26/20261126_230039/server-01/events.jsonl` and `client-01/events.jsonl`. The run transition and missing client/workload alignment are recorded as confounders in the spec and resource issue.
