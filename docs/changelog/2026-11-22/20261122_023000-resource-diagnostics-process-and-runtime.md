# MiMITA resource diagnostics and evidence-backed next steps

## Runtime and process evidence

- Captured a 10-second Windows process CPU sample on a 12-logical-CPU machine. Six concurrent `mimita.exe` processes used a combined 737% of one core (7.37 core-equivalents, about 61.4% of machine capacity): PID 30496 316.7%, PID 2744 103.3%, PID 26748 86.2%, PID 25204 79.1%, PID 29824 78.6%, PID 32060 73.1%. They mapped to the root FCS session, an additional FCS NPC objective run, and a separate TDM run. The root dev-loop listed the shared server but reported its client offline; do not infer all six are one game or one run. They were left untouched.
- Root server run `20261122_011031`, PID 26748, journal `logs/2026-11-22/20261122_011031/server-01/events.jsonl`, had zero connected players but 19 live FCS NPCs and 169 active projectiles. Its latest `performance.server-tick-window` covered 1.274 s / 5 ticks: actual loop rate 3.925 Hz, total tick average 223.87 ms, p95/p99 468.74 ms, NPC average 205.59 ms and max 467.52 ms; 60% of sampled ticks exceeded 100 ms. The corresponding `server-loop-window` also reported 5 ticks and 1272.7 ms average loop time. `npc.server-phase-window` reported 358.13 ms of NPC work in its window. A world-phase sample reported NPC simulation 400.53 ms, physical contact 366.51 ms, and projectile work 198.46 ms for 2 ticks in 1.071 s. These diagnostics directly identify playerless NPC simulation and their active combat/projectiles as the first server-side target.
- Root client journal `logs/2026-11-22/20261122_011031/client-01/events.jsonl` recorded about 37–51 frames per 200 ms window (roughly 185–255 FPS) while `config/video-settings.json` sets `maxFrames=999` and forces VSync off. The sampled `performance.frame-slice` attributed 135–162 ms/window to the inclusive `EngineTick::Render` scope (nested `Rendering` was 95–113 ms/window) and 14–29 ms/window to config polling in some windows. The existing owner `src/engine/engine-tick-setup.cpp` throttles config polling to five groups every 500 ms; measure each group before changing that cadence. The client data supports testing a lower cap, but the earlier 240 FPS experiment was not controlled and did not show reliable savings.
- The concurrent game processes alone occupied about 61% of machine CPU in the sample; dashboard/daemon and development tools added more. No compiler/linker process was present in the measured process list. This makes CPU contention a credible contributor to slow builds, but no build ran during this sample and no matched low-load/high-load build comparison proves causality.
- The root dev-loop still identified the active EXE as stale relative to current source. The prior resident server logging aggregation change remains unverified; this diagnostic run tested the existing live artifact, not that source change.

## Recommended sequence

1. Make a safe playerless-server idle path: retain room discovery, sockets, and the responsive server loop, but pause or strongly throttle NPC decision/movement/combat, autonomous projectile/contact simulation, and unnecessary snapshots while no human players are connected. Resume promptly when a player joins. Preserve the authoritative 60 Hz path during active play. Confirm gamemode requirements before selecting which NPC state may freeze.
2. On one owned client, compare 999 FPS to 144 and 120 FPS under the same scene and player/NPC load. Record CPU, FPS percentiles, input feel, and journal frame scopes; choose the lowest acceptable cap. Keep VSync forced off.
3. If client CPU remains high after capping, profile the individual config-poll groups in `src/engine/engine-tick-setup.cpp`; current windows show a measurable cost but it is secondary to render and must be attributed before refactoring.
4. Re-run the same incremental build once with unnecessary game/test runs quiescent and once under the normal workload. Record build request-to-start, preflight, compile, link, and publish separately. This is required to establish how much CPU contention explains build delay.

No source behavior was changed in this diagnostic session. The active CPU issue remains open; there is enough evidence to prioritize the playerless FCS simulation path, followed by a matched frame-cap experiment and controlled build comparison.
