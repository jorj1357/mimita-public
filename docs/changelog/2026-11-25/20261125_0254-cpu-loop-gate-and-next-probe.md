# CPU reduction loop: measured pressure and probe gate

## Result

This pass adds no gameplay code and makes no CPU-reduction claim. It narrows the next measurement to the already-running 67-NPC Juggernaut server and records why a code treatment is not yet safe: the root dev-loop registry says its instances are dead, six `mimita.exe` processes are actually alive in three parent groups, and the existing function CPU probe produced no rows. The exact run owner and command route must be reconciled before probing.

- Win32 PID-only host/process sample: `.dev/perf-captures/cpu-four-pid-winapi-postbuild-20261125T023658Z.csv`, 2026-11-25 02:36:59.1648641–02:37:13.6632485 UTC (15.49 s), 12 logical CPUs, no build active. Host CPU mean 99.985%; available RAM mean 630.2 MB/min 513.9 MB; pagefile use mean 37.02 GB.
- In that sample, the known Juggernaut client PID 25552 used 14.261% whole-host CPU and server PID 36452 used 16.381%, together 31.642%. A separate Bloodtest client/server pair used 20.207% combined. The measured four-process total was 50.849% host. These are process CPU measurements, not function attribution.
- The same-window server journal identifies Juggernaut Horde on `dust2cyberiav4`, 67 NPC and 1 player. `performance.server-tick-window` reported 15-tick windows averaging 75.94–83.21 ms; 33–40% of reported ticks exceeded 100 ms. This fails the 16.667 ms tick budget by a wide margin.
- `npc.phase-window` at `src/npc/npc.cpp:4437` reported 743 `updateOneNpc` updates and 435.54 ms aggregate elapsed time, including physics 138.51 ms, collision 100.39 ms, decision 66.58 ms. `npc.server-phase-window` at `src/network/server-npcs.cpp:3377` reported `simulateSharedNpcs`: 583.10 ms across 10 ticks, AI 514.36 ms, and 167 target scans. These are scoped elapsed times, not CPU milliseconds; nested scopes may overlap and must not be summed as CPU.
- No `performance.cpu-callsite-window` rows were found for this run. The existing 1/64 callsite probe is therefore still unproven on this pair. A separate 2-NPC Bloodtest run estimated `updateOneNpc` at 2.46% of server CPU from 27 sparse samples; that result cannot be generalized to this 67-NPC workload.
- Root latency owner reported game-DLL attempt `game-dll-20261125T023802184416Z-39264c`, generation 635, ran 255.459 s with host CPU 99.93% and minimum available RAM 49.8 MiB. Three process pairs were present; the target Juggernaut pair averaged 29.02% host during that build. This is build-pressure correlation, not proof that MiMITA load caused the build duration. Fresh client FPS after publication was 13.8–31.4 with p95 67–117 ms; the server host DLL reported g635 while NPC module remained g632. This build had no CPU treatment and is not an A/B.

## Decision and next discriminating step

Do not change collision, AI, or logger behavior from phase wall-time alone. First reconcile the stale root registry and exact ownership of run `20261125_014732` (server 36452, client 25552); then run the already-built bounded callsite probe once on that same pair, with a fresh writable journal sink and no build overlap. Select exactly one treatment from the attributed CPU data. The next root game-DLL build must carry only that CPU treatment as the experimental variable, and its before/after comparison must retain process CPU, function CPU estimate, every client frame against 4.167 ms, server ticks against 16.667 ms, and gameplay correctness evidence. If the probe cannot run safely, fix or document the command/ownership path before changing gameplay code.

## Uncertainty

These data support the user's report that MiMITA processes materially consume host CPU and coincide with poor responsiveness. They do not prove that closing MiMITA alone caused the perceived speedup, identify the dominant source function by CPU cycles, or establish 240 FPS / 60 Hz acceptance. The low free-memory and high pagefile observations indicate memory pressure, but paging as the cause of CPU/build slowdown remains unproven.
