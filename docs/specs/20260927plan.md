### Why the new system pushes you too far

In [actor-triangle-solver.cpp](C:/mimita-v9/src/physics/movement/actor-triangle-solver.cpp), every body/arm/weapon triangle contact currently calls:

```cpp
respondVelocityAgainstNormal(player, c.normal, c.sweepDelta, true, ...)
```

That treats an arm touching a wall like a moving impact. The arm’s movement becomes outward player velocity, causing the large bounce.

To match the old feel:

- Keep exact triangle hitboxes.
- Use triangles to detect penetration and block movement.
- Apply only small depenetration.
- Project velocity along the surface instead of bouncing.
- Do not use arm/weapon sweep velocity as player bounce.
- Only moving physical objects should transfer velocity to the player.
- Keep explosions, weapons, and knockback as separate intentional forces.

This gives exact collision geometry without changing the old movement feel.

### Main performance problems

The likely costs are:

1. Every actor triangle is compared against every nearby world candidate triangle.
2. The solver can repeat this up to four times.
3. Mesh arrays are copied and transformed every solver iteration.
4. Body, arms, legs, head, and weapon all share a broad candidate list, including irrelevant triangles.
5. The weapon render mesh can contain hundreds of triangles.
6. Physical entities currently create a temporary collision world per overlapping object in [physical-entity.cpp](C:/mimita-v9/src/physics/physical-entity.cpp).
7. Physical object movement currently advances from the render path instead of only the fixed 60 Hz simulation path.

The biggest optimization should be:

- broadphase AABB filtering per actor part;
- cached candidate lists;
- reusable scratch memory;
- simplified collision meshes for arms/legs/weapon while preserving exact authored hitbox shapes;
- one solver iteration when there is no penetration;
- no temporary `World` creation for crates.

### Overall plan

#### Phase 1 — Restore old movement feel

Keep the actor-triangle solver active.

Change only the response policy:

- static world contacts: depenetration + velocity projection;
- arm/leg/head contacts: no bounce;
- weapon contacts: no bounce;
- moving platforms/crates: support velocity and controlled push;
- explosions and weapon forces: unchanged.

Acceptance:

- walk directly into a block;
- enter the block corner with arms extended;
- slide along walls;
- no large outward launch;
- no limb stuck;
- exact triangles still visibly stop at geometry.

#### Phase 2 — Remove the performance spikes

Add collision diagnostics for:

- actor triangle count;
- candidate world triangle count;
- triangle tests;
- solver iterations;
- per-part milliseconds;
- physical-entity candidate count.

Then optimize in this order:

1. reject world candidates against each individual body-part AABB;
2. deduplicate candidate triangle IDs;
3. reuse vectors and scratch buffers;
4. cache transformed actor triangles for the tick;
5. avoid copying every mesh on every solver iteration;
6. reduce iterations when the actor is not penetrating;
7. replace temporary physical-entity worlds with direct triangle queries.

Do not disable exact triangles. Make the broadphase cheaper and the narrowphase smaller.

#### Phase 3 — Persistent physical-object foundation

Create one authoritative persistent object record:

- stable object ID;
- transform;
- velocity;
- collision shape;
- render model/material;
- mass;
- friction;
- strength/health;
- destructible flag;
- ownership/network state;
- persistence ID.

The existing `PhysicalEntitySystem` should become the owner instead of remaining a separate temporary crate system.

Crates should support:

- spawn;
- save/load;
- render using existing game textures/materials;
- collision;
- walking on top;
- jumping from them;
- pushing them;
- shooting them;
- server-authoritative state;
- client interpolation.

#### Phase 4 — Moving objects

Implement fixed-tick object movement:

- static;
- kinematic;
- pushable;
- dynamic later.

Player interaction should be:

- walking into crate → crate receives controlled push;
- standing on crate → player receives support velocity;
- jumping from crate → preserves platform momentum;
- collision → uses the same triangle/contact response rules.

No render-frame physics.

#### Phase 5 — Combat and destructible objects

Start with simple destructibility:

- crate health/strength;
- projectile impact point;
- material-dependent damage;
- damage threshold;
- break event;
- replacement fragments or pre-authored damaged states.

For “shoot a hole in it,” do not begin with arbitrary runtime mesh surgery. Start with:

- authored destructible pieces;
- material sections;
- breakable panels;
- chunk removal;
- pre-authored hole variants.

That will be much more reliable and networkable than deleting arbitrary triangles at runtime.

#### Phase 6 — Materials and editing

Make object properties JSON-controlled:

```json
{
  "material": "wood",
  "strength": 100,
  "mass": 20,
  "friction": 0.7,
  "pushable": true,
  "destructible": true
}
```

Then add editor commands for:

- changing material;
- changing strength;
- changing mass;
- changing collision shape;
- moving/rotating objects;
- saving the world;
- reloading changes live.

#### Phase 7 — Networking and persistence

The server owns:

- object creation;
- transforms;
- velocity;
- damage;
- destruction;
- object IDs;
- save/load state.

Clients receive snapshots and interpolate visual motion. The same physics/contact routines should be shared by client, server, replay, and tests.

The first implementation target should be:

> One persistent wooden crate that renders correctly, can be walked on, pushed, jumped from, damaged, and saved/reloaded.

After that works, expand to moving platforms, metal/stone materials, breakable panels, and larger destructible structures.
