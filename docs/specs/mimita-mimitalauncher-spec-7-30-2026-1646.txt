1. Product definition
MiMITALauncher.exe is the single official entrance into MiMITA.
The user should always start MiMITA through:
MiMITALauncher.exe
The launcher is simultaneously:
* The first-time installer
* The game launcher
* The updater
* The file-health checker
* The repair system
* The uninstaller
* The installation manager
* The crash and launch-log collector
* The future foundation for the complete MiMITA platform
The user should never need to manually locate or directly start mimita.exe.
The launcher owns the process of preparing MiMITA and then starts mimita.exe automatically.

2. Core user experience
Normal launch
When an existing user opens MiMITALauncher.exe:
1. A small launcher window appears immediately.
2. It checks the local installation.
3. It checks whether an update is available.
4. It shows a white progress bar.
5. When everything is ready, the progress bar reaches 100% and turns green.
6. It automatically starts mimita.exe.
7. The visible launcher window disappears.
8. The launcher remains running silently in the background to monitor the game. and its super lightwieght it should cost as minimal processing power as possible
Example:
MiMITA


Checking files...
Checking for updates...
Everything looks good.


████████████████████ 100%


Starting MiMITA...
The healthy path should require:
0 additional clicks
The user double-clicks the launcher and enters the game.

* Installed in more than one location
* Installed but currently unavailable

For the first implementation, the launcher may detect installation using:

version.txt
mimita.exe

7. Update behavior
Normal update check
Every time the launcher starts:
1. Read the installed version.
2. Download the small current-version manifest.
3. Compare installed official files against the manifest.
4. Determine which files changed.
5. Download only the changed files.
6. Validate downloaded files.
7. Install the update.
8. Start MiMITA.
The launcher must not redownload the entire game because one file changed.
Delta-style file updating
For the first version, “only changed files” means:
* Compare each file hash against the official manifest.
* Download only files whose hashes differ or that are missing.
* Leave matching files untouched.
Later, binary patches may update only the changed bytes inside large files.
That is optional. File-level differential updates are sufficient for the first reliable version.
Update prompt
For the current version, updates are checked immediately when launching.
When an update is available:
A MiMITA update is ready.


Version 2.1.0


[Install update]
[Play without updating]
Pressing Enter selects:
Install update
The safest normal path is updating before playing.
Background preparation
The update may download and prepare in the background while the launcher is visible.
However, files actively used by the running game must not be replaced while the game is running.
A prepared update may be staged and applied during the next launch.
Offline behavior
If the launcher cannot reach the update service:
MiMITA could not check for updates.


Starting your installed version.
The launcher should automatically start the installed game when possible.
No internet must not prevent offline play.
________________


8. Transactional updates
Updates must never leave the working installation half-updated.
Use a staged update process:
1. Download files into a staging directory.
2. Verify every downloaded file.
3. Confirm sufficient required files are present.
4. Prepare the new version.
5. Atomically switch the active installation to the new version.
6. Preserve the previous working version for rollback.
Example directories:
%LOCALAPPDATA%\MiMITA\
    installations\
        stable-2.0.0\
        stable-2.1.0\
    user-data\
    launcher-data\
    active-installation.json
This directory model makes the following features easier:
* Safe updates
* Rollback
* Repairs
* Multiple installations
* Beta channels
* Moving the installation
* Preserving mods
* Avoiding damage to the currently working version
________________


9. Repair behavior
Repair must never destructively overwrite a user's modified installation.
If the launcher detects damage:
1. Preserve the existing installation.
2. Create a separate fresh installation directory.
3. Download or reconstruct the official version there.
4. Verify the new installation.
5. Start the fresh installation.
6. Keep the old installation available.
7. Clearly label the old installation as damaged or modified.
Example:
MiMITA found a problem with the current installation.


Your existing files will not be changed.


Creating a clean copy...
Possible directory result:
MiMITA\
    installations\
        original-modified-copy\
        repaired-2.1.0\
The launcher should not assume a difference is damage.
A difference may be:
* A mod
* A user experiment
* A custom executable
* A development build
* A corrupted file
Therefore, the old installation must remain intact unless the user explicitly chooses to delete it.

10. Failure handling
No internet
Behavior:
Update check unavailable.
Launch the installed version automatically.
Allow offline play.
Do not block launch merely because the internet is unavailable.
Insufficient disk space
If the currently installed game is launchable:
There is not enough space to install the update.


Starting your current version.
Offer:
[Free space help]
[Change installation location]
[Play current version]
The default action should launch the current version.
If MiMITA is not installed yet, installation cannot continue, so show a simple explanation and allow the user to select another drive.
Permissions problem
Show:
MiMITA could not write to this folder.


[Fix automatically]
[Choose another folder]
[Send problem]
The launcher should first attempt safe automatic recovery.
Because the default path is inside %LOCALAPPDATA%, normal installation should usually not require administrator privileges.
Antivirus or security software interference
Show:
Your computer stopped MiMITA from opening or updating.


[Try again]
[Show fix]
[Send problem]
[Play current version]
The launcher should collect non-sensitive diagnostics such as:
* Launcher version
* Operating system version
* Failed file path
* Error code
* Operation attempted
* Timestamp
* Whether the file exists
* Whether writing or execution was denied
The report must not upload personal files without explicit permission.
API or update-server outage
Show:
MiMITA services are temporarily unavailable.


You can still play offline.


[Start MiMITA]
[Service status]
[Send problem]
The launcher should automatically start the game if an installed version works.
Corrupted launcher
A corrupted launcher cannot reliably repair itself while executing.
Use several layers of protection:
1. Digitally sign the launcher.
2. Publish the official launcher hash.
3. Let the website verify and redownload the launcher.
4. Include a small external bootstrap or recovery mechanism later.
5. Make mimita.exe capable of directing users to the official recovery page when launched without a healthy launcher.
6. Keep the launcher itself small and stable.
7. Avoid updating the active launcher directly without a staged replacement.
For the first version, the recovery message can be:
This MiMITALauncher file appears damaged or outdated.


Download a fresh copy from:
mimita.fun/download
A README.txt beside the installation may contain the same recovery instructions.

13. Launcher background process
After starting mimita.exe, the launcher remains hidden.
This means the initial Windows implementation will normally involve two operating-system processes:
MiMITALauncher.exe
mimita.exe
The product still has one user-visible entrance.
The important rule is:
One entrance does not require literally one operating-system process.
Trying to force the launcher and game into one process would make crash isolation, updating, recovery, and monitoring less reliable.
Background responsibilities
While the game is running, the hidden launcher may:
* Detect whether the game exits normally
* Detect crashes
* Record launch duration
* Save crash metadata
* Offer to send a crash report
* Restart the game when explicitly requested
* Apply a staged update after the game closes
* Restore the previous version after a failed update
Resource requirements
While monitoring the game, the launcher must:
* Use nearly zero CPU while idle
* Avoid polling every frame
* Avoid GPU usage
* Avoid continuous disk writes
* Avoid constant network requests
* Sleep while waiting for process events
* Use operating-system process-wait mechanisms
* Keep memory usage small
* Batch logs rather than writing every millisecond
Target behavior:
CPU while idle: approximately 0%
GPU while idle: 0%
Network while idle: 0 B/s except occasional required service checks
Disk while idle: no continuous writes
The launcher does not need to watch game health at 60 Hz.
It can wait for:
* Process exit
* Crash signal
* Operating-system event
* Occasional low-frequency heartbeat
* Explicit IPC message from the game

24. Cross-platform strategy
The immediate goal is Windows.
Future platforms may include:
Windows
Linux
macOS
Android
iPhone and iPad
VR systems
Consoles
Web-compatible environments
Other future devices
The realistic cross-platform rule is:
One universal behavior specification.
Platform-specific executables where necessary.
Shared core logic wherever practical.
A single binary file format that executes natively on every operating system does not currently exist in a practical way.
Different operating systems require different:
* Executable formats
* Signing systems
* Permission models
* Installation systems
* Update restrictions
* Sandboxing rules
* App-store requirements
Therefore:
Windows: MiMITALauncher.exe
macOS: MiMITALauncher.app
Linux: AppImage, Flatpak, package, or native launcher
Android: APK or app bundle
iOS: signed iOS application
They should all follow the same product behavior and shared protocol.
The launcher architecture should separate:
Launcher core
Platform integration
User interface
Update transport
Installation storage
Game process control
This allows the universal specification to remain stable while each platform implements the necessary native details.

28. Security requirements
The launcher must:
* Use HTTPS for downloads
* Validate a signed update manifest
* Verify SHA-256 hashes before activating files
* Digitally sign official launcher releases
* Never execute partially downloaded files
* Never silently execute arbitrary content from an update response
* Protect account tokens if account support is added later
* Avoid requiring administrator permissions when unnecessary
* Treat server responses as untrusted until validated
* Store no secrets in plain-text logs
* Prevent path traversal from manifest paths
* Prevent update files from writing outside the selected installation directory
User modification support must not mean update-system insecurity.
Official builds, modified builds, and user content should remain clearly distinguishable.

30. Acceptance tests
Existing healthy user
Given MiMITA is installed and current
When the user opens MiMITALauncher.exe
Then the launcher visibly checks the installation
And displays a green 100% state
And automatically starts mimita.exe
And requires no additional clicks
First-time user
Given MiMITA is not installed
When the user opens MiMITALauncher.exe
And repeatedly presses Enter
Then MiMITA installs to %LOCALAPPDATA%\MiMITA
And a launcher shortcut is created
And mimita.exe starts
Available update
Given an update exists
When the launcher starts
Then it shows an update prompt
And Enter selects Install update
And only changed files are downloaded
And the update is verified before activation
And MiMITA starts after completion
No internet
Given MiMITA is already installed
And the update service cannot be reached
When the launcher starts
Then it does not block the user
And it automatically starts the installed game
Modified installation
Given the user modified official game files
When the launcher detects differences
Then it does not destroy the modified installation
And it may create a separate clean installation
And the user's old files remain available
Failed update
Given an update download or validation fails
When a previously working installation exists
Then the working installation remains unchanged
And the launcher starts that version when possible
Game crash
Given mimita.exe exits unexpectedly
When the launcher detects the exit
Then it records the exit code
And preserves useful logs
And offers restart and feedback options
Resource usage
Given mimita.exe is running normally
When MiMITALauncher.exe is hidden
Then the launcher uses no GPU
And approximately zero CPU while idle
And performs no continuous disk writes

31. Absolute design laws
1. MiMITALauncher is the one official entrance into MiMITA.


2. Healthy returning users should reach the game with zero extra clicks.


3. A first-time user can install by pressing Enter repeatedly.


4. The launcher must never require an account.
